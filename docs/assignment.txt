과제 1. 카메라 연동과 기준선
상황
카메라 영상은 끊기고, 늦어지고, 어두워진다. 추론이 아무리 정확해도 들어오는 프레임이 3초 전 것이면 쓸모가 없다. 웹캠·IP 카메라·동영상 파일은 들어오는 경로가 다 다른데, 뒤의 코드는 입력이 무엇이든 똑같이 돌아야 한다.

해결할 것
웹캠 1대와 IP 카메라(없으면 가짜 카메라)를 보드에 연결하고, 각 입력에서 실측 FPS·해상도·첫 프레임 지연을 잰다.
수신 루프를 두 가지로 만들어 비교한다 — (a) cv2.VideoCapture.read()를 그대로 반복, (b) 별도 스레드가 읽고 최신 1장만 남기는 리더. 각각에 0.2초 처리 지연을 넣고 2분 뒤 체감 지연을 비교한다.
카메라를 뽑았다 꽂아도 프로그램이 죽지 않고 스스로 복구되게 한다.
화면→화면(glass-to-glass) 지연을 웹캠 직접 입력과 RTSP 입력에서 각각 잰다.
헤드리스 보드에서 결과를 PC 브라우저로 본다.
확인 기준
T0-1~T0-6 전부 합격 (준비·기능 테스트 2장)
(a)와 (b)의 2분 뒤 지연 차이를 숫자로 보고, 원인을 설명한다
재연결 시험에서 프로세스 재시작 없이 30초 안에 복구
산출물
연결 시험 기록(입력별 FPS·해상도·첫 프레임 지연·CPU 사용률)
지연 측정표(리더 방식 × 입력 종류, glass-to-glass 포함)
생각해 볼 점
카메라가 30fps를 보내는데 추론이 10fps면 1분에 몇 장이 버려지나? 버리지 않으면 무슨 일이 생기나?
IP 카메라는 메인 스트림(1080p)과 서브 스트림(720p) 중 어느 것을 추론에 쓰는 것이 맞나? 재실 인원처럼 먼 사람을 봐야 할 때는?
Orin Nano에 하드웨어 인코더(NVENC)가 없다는 사실은 설계에 어떤 영향을 주나?
심화(B)
GStreamer 파이프라인을 직접 써서 NVDEC 하드웨어 디코딩(--backend gst)과 CPU 디코딩의 CPU 사용률·FPS를 1080p 입력에서 비교한다.
Windows 또는 Linux PC의 웹캠을 RTSP로 송출하는 스크립트를 만들어(macOS 전용 fake_camera.sh webcam을 이식) 보드에서 실시간 추론한다.
확인 문제 1
1-1. appsink drop=true max-buffers=1 sync=false 세 옵션이 각각 하는 일을 한 줄씩 쓰라. 1-2. RTSP 전송을 UDP에서 TCP로 바꾸면 무엇이 좋아지고 무엇이 나빠지나? 1-3. IP 카메라의 GOP(I-프레임 간격)를 FPS와 같게(1초) 두라고 권장하는 이유는? 1-4. CSI 카메라·USB 웹캠·IP 카메라 중 보드 CPU 부하가 가장 작은 것과 그 이유를 쓰라. 1-5. 리더(b)를 썼는데도 e2e 지연이 300ms다. 그중 코드가 줄일 수 없는 부분은 어디인가?

과제 2. 물체 인식
상황
사전학습 모델(COCO 80종)은 사람·의자·노트북은 잘 보지만, 실습실의 소화기·멀티탭·멀티미터는 모른다 — 그리고 모르는 물체에 비슷한 라벨을 자신 있게 붙인다. 보드에서는 속도도 문제다. PyTorch 모델을 그대로 돌리면 카메라 FPS를 못 따라간다.

해결할 것
YOLO 모델을 TensorRT 엔진(FP16, INT8)으로 변환하고, PyTorch 원본과 추론 시간·FPS·정확도(mAP)·전력을 비교한다.
조명(밝음/어두움)과 거리(2/5/8m)를 바꿔 사람 검출 신뢰도가 어디서부터 무너지는지 표로 만든다.
추적(ByteTrack)으로 같은 사람에게 같은 ID를 유지하고, 가상 선 통과를 IN/OUT 한 번만 세어 MQTT로 발행한다.
COCO에 없는 물품 5종을 골라 세 방식으로 인식한다 — ① YOLO 라벨 그대로 ② YOLO 박스를 이미지 임베딩으로 재라벨 ③ 텍스트로 클래스를 지정하는 개방 어휘 검출(YOLOE). 방식별 정답률과 오인식 사례를 수집한다.
확인 기준
FP16 엔진 추론 ≤ 10ms, 카메라 FPS 이상으로 처리
선 통과 10회(IN 5/OUT 5) 오차 ≤ 1
벤치마크 표 4행(PyTorch / FP16 / INT8 / 큰 모델 FP16) 완성, INT8의 mAP 하락 폭을 보고
개방 어휘로 5종 중 4종 이상 정확
산출물
벤치마크 표(평균·p95 ms, FPS, mAP50-95, 전력, 메모리)
조명×거리 신뢰도 표
물품 인식 비교표(방식 × 물품, 오인식 사례 사진 5장 이상)
생각해 볼 점
INT8이 FP16보다 빠른데도 기본값으로 쓰지 않는 이유는? INT8 보정 데이터를 현장 프레임으로 바꾸면 무엇이 달라질까?
검출 신뢰도 임계값(--conf)을 0.5에서 0.25로 내리면 무엇이 늘고 무엇이 줄까? 재실 인원과 물품 점검에서 각각 어느 쪽이 맞는 선택인가?
추적 ID가 바뀌는 상황을 세 가지 들고, 각각 카운팅에 어떤 오류를 만드는지 쓰라.
개방 어휘 검출에 "red fire extinguisher"와 "fire extinguisher"를 넣었을 때 결과가 다른 이유는?
심화(B)
현장 스냅샷 100~300장을 라벨링해 YOLO를 파인튜닝하고, 개방 어휘 검출과 정확도·속도를 비교한다. 어느 쪽을 택할지 근거와 함께 쓴다.
DeepStream으로 같은 카메라·같은 모델을 돌려 Ultralytics 방식과 FPS·CPU·전력·지연을 비교한다. 4채널(가짜 카메라 4개)에서 다시 비교한다.
확인 문제 2
2-1. .pt → .engine 변환이 빨라지는 이유를 세 가지 쓰라. 엔진 파일을 다른 보드에 복사해 쓰면 안 되는 이유는? 2-2. 벤치마크에서 평균보다 p95 지연을 함께 보라는 이유를 상시 서비스 관점에서 설명하라. 2-3. 선 통과 판정은 박스 하단 중앙이 선의 어느 쪽인지를 외적 부호로 구한다. 박스 중심을 쓰지 않는 이유는? 위→아래로 그은 선에서 왼→오 이동은 IN이다. OUT으로 바꾸려면 코드를 고치지 않고 무엇을 바꾸나? 2-4. 한 사람이 선 위에서 멈췄다가 되돌아갔다. IN·OUT 카운터는 어떻게 되고, 그것은 버그인가? 2-5. app.py의 relabel 모드는 유사도가 0.20 미만이면 YOLO 라벨을 유지한다. 이 임계값을 없애면 어떤 문제가 생기나?

과제 3. 재실 인원 카운터
상황
"지금 3강의실에 몇 명이 있나"는 간단해 보이지만, 사람은 앉고, 겹치고, 책상에 가려지고, 뒷자리는 화면에서 30픽셀이다. 반대로 포스터의 사람 사진과 모니터 속 사람을 세기도 한다. 결과는 CO₂ 예측·냉난방 제어·회의실 노쇼 판정에 들어가므로 틀리는 방향이 중요하다 — 빈 방을 '있음'으로 보면 냉방이 안 꺼지고, 있는 방을 '없음'으로 보면 사람 있는데 냉방이 꺼진다.

해결할 것
방식을 정한다 — 방 안을 직접 세는 직접 계수와 문에서 IN−OUT을 누적하는 출입 계수. 각각의 약점(가림 / 누적 드리프트)을 시험으로 확인하고, 우리 방에 맞는 방식(또는 혼합)을 근거와 함께 고른다.
카메라를 설치한다 — 높이·각도·역광을 바꿔 보며 설치가 정확도에 미치는 영향을 기록한다.
세는 영역(include)·제외 영역(exclude)·구역(zone)을 그리고, 사람 위치 판정점(발/몸 중심)을 정한다.
먼 자리의 작은 사람을 살린다 — 입력 크기 640/960, 조각 검출 1x1/2x2를 비교한다.
시간 평활(--window, --stat)을 정한다 — 안정성과 반응 속도의 맞교환을 표로 보인다.
정확도를 평가한다 — 30분 이상 시험 운영, 정답 시트 30개 이상, MAE·편향·±1명 비율·빈 방 오판율.
MQTT로 발행한다(retain). 새 구독자가 접속 즉시 현재값을 받아야 한다.
확인 기준
MAE ≤ 1.0명, ±1명 이내 ≥ 80%, 빈 방 오판율 ≤ 10%
편향(+/−)의 원인을 가림·크기·오검출 중 무엇인지 사례로 설명
출입 계수와 직접 계수를 30분 동시 운영하고 차이와 원인을 설명
산출물
재실 인원 서비스(MQTT 발행 중) + 구역 설정 파일
정확도 평가서(평가 조건, 지표, 오차 원인 분류, 인원 규모별 오차)
설계 변수 비교표(imgsz × tiles, window × stat)
생각해 볼 점
평가용 정답은 누가, 어떻게 세어야 공정한가? 예측값을 보고 세면 무엇이 문제인가?
창(--window)이 30초면 사람이 들어온 뒤 몇 초 만에 값이 바뀌나? 냉난방 제어에는 괜찮고 자동문에는 안 되는 이유는?
빈 방 판정만 따로 길게(5분 연속 0) 잡으라는 이유는? 이 규칙이 만드는 새로운 오류는?
천장 수직(어안) 카메라는 왜 사전학습 모델이 잘 못 보나? 그래도 써야 하면 무엇을 해야 하나?
심화(B)
BRIO 4K + 하드웨어 JPEG 복원(hw=1) + 2x2 조각과 IP 카메라 1080p의 재실 인원 정확도를 같은 방·같은 시간에 비교한다.
재실 인원을 입력 특징으로 넣은 60분 CO₂ 예측과 뺀 예측을 비교해 "재실 인원 1명이 CO₂를 얼마나 올리는가"를 숫자로 답한다(시계열 추론 실습 연계).
출입 계수를 직접 계수로 주기 보정하는 혼합 방식을 구현하고, 하루 운영 뒤 드리프트가 얼마나 줄었는지 보인다.
확인 문제 3

과제 5. 거리 측정 (웹캠 2대)
상황
사람은 두 눈으로 거리를 안다. 카메라 두 대로 같은 일을 하려면 두 카메라의 정확한 관계(간격·회전·초점거리)를 알아야 하고, 그것을 알아내는 것이 보정이다. 보정이 조금 틀어지면 거리가 수십 cm 틀어지고, 자동 초점이 한 번 움직이면 보정은 무효가 된다. 그리고 거리 오차는 거리의 제곱으로 커진다.

해결할 것

체커보드 25쌍을 고루 촬영해 보정하고, 재투영 오차·기준선·정렬 후 행 차이로 품질을 판정한다. 나쁘면 재촬영한다.
1.0/1.5/2.0/3.0/4.0m에 물체를 두고 측정 오차를 잰다. 보정이 출력한 예상 오차 표와 비교한다.
측정이 안 되는 조건(무늬 없는 벽·역광·너무 가까움·빠른 움직임)을 찾아 대응을 기록한다.
YOLO와 결합해 사람마다 거리를 낸다.
확인 기준

실측 오차: 1~2m ≤ 5%, 3m ≤ 8%, 4m ≤ 12% — 그리고 예상 오차 표와의 일치 여부 설명

산출물
보정 파일 + 보정 품질 보고(지표·촬영 분포 사진)
